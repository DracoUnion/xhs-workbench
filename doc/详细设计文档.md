## 二、领域模型（DDD）

### 2.1 限界上下文划分

```
┌ Platform(平台支撑) ┐        ┌ Orchestration(任务编排) ┐
│ User · Settings ·  │        │ AgentDef · AgentRun ·   │
│ RiskConfig         │        │ ReviewPoint · Dedup     │
└────────┬───────────┘        └──────────┬──────────────┘
         │                               │
┌────────▼───────────┐   ┌───────────────▼──────────────┐
│ Discovery(需求发现)  │   │ Production(产品制作)          │
│ Account · Ranking   │   │ Product · Material ·         │
│ Direction · Product │   │ DesignDoc · Build            │
└────────┬───────────┘   └───────────────┬──────────────┘
         │                               │
┌────────▼──────────────┐  ┌─────────────▼──────────────┐
│ Content(内容获客)       │  │content_packages/skills  ↘↘│
│ Keyword · Note ·       │  │（跨上下文共享聚合，见2.5）  │
│ Template · Skill ·     │  │                             │
│ ContentPackage · Review│  │                             │
└────────────────────────┘  └─────────────────────────────┘
```

- **上下文职责边界**：Discovery 只产出「已验证的方向证据」；Production 消费方向落地为产品；Content 消费产品产出内容；三大链路都通过 Orchestration 复用自己的 Run 上报进度与检查点。

### 2.2 聚合与标识

| 聚合 | 聚合根 | 内含实体 | 标识（业务键） |
|------|--------|---------|----------------|
| Account | `Account` | AccountMetrics | `xhs_user_id` |
| Product | `Product` | ProductImage | `xxlink_id`（商品分享短链解码后的 id） |
| Direction | `Direction` | DirectionAccount | `name`（品类×形态合成） |
| Keyword | `Keyword` | — | `(product_id, word)` |
| Note | `Note` | NoteImage / NoteFrame / Transcript / NoteAnalysis | `note_id` |
| Template | `Template` | — | `(product_id, cluster_key)` |
| Skill | `Skill` | SkillVersion | `(product_id, name)` |
| ContentPackage | `ContentPackage` | Review | `(skill_id, seq)` |
| AgentRun | `AgentRun` | ReviewPoint | `run_id`（UUID） |

### 2.3 实体关键属性（领域层）

```
Account.userId、nickname、fans、score
AccountMetrics.evidenceScore(sub: 成交/转化/阅读) · trustBonus(上榜天数/进榜类型数) · lowFansBonus · breakdown(JSON)
Product.title、priceCents、sales、spec、desc、images[]、form(enum) 、status(采集/采集失败/校验通过/已分析)
Direction.name、category、form、status(观察中/升温/已验证/降温/放弃) 、evidenceText
Note.title、body、topics[]、author、interactions{likes,collects,comments}、mediaType(图文/视频)、aToZGroup
NoteAnalysis.titleFormula、structure、hookType、coverRule、interactionFeature
Template.clusterKey、supportedCount、draftMd、status(草稿/已转Skill)
Skill.md、filesWhitelist[]、rules{标题/正文/话题/图片/禁用词}、status(draft/testing/active)、reviewPolicy(manual/auto)
ContentPackage.title、body、topics[]、images[]、status(draft/reviewing/approved/rejected)
AgentRun.status(枚举见6.3)、context(JSONB)、checkpoint、log[]
```

### 2.4 领域服务与仓储接口

```python
# 定位在 app/domain/services/
class AccountScoringService:        # 纯函数，无 I/O

class DirectionClusteringService:   # 主 Agent 汇总
    def cluster(products: list[Product]) -> list[DirectionProposal]: ...
    def transition(state, evidence) -> DirectionStatus: ...   # 状态机

    def fingerprint(note_id: str, product_id: int) -> str: ...
    def is_duplicate(product_id, fingerprint) -> bool: ...

class ContentReviewCoordinator:     # 生成↔审查轮转
    def request_review(pkg: ContentPackage) -> None: ...
    def apply_verdict(pkg, verdict, rounds) -> ActionResult: ...

class RiskDelay:                    # 反风控节奏
    def wait(source: str, ctx) -> None: ...                # 60~90s + jitter
```

```python
# 仓储端口（实现位于 app/repositories/）
class AccountRepository:    add / by_xhs_id / top_n(score, limit) / metrics(account_id)
class ProductRepository:    add_batch / by_direction / by_account / link_count(account_id)
class DirectionRepository:  upsert_proposal / by_status / attach_accounts(...)
class KeywordRepository:    upsert / by_product / collect_stats(product_id)
class NoteRepository:       add_or_skip_dedup / by_keyword / unanalyzed(product_id) / with_links_for_cluster(...)
class SkillRepository:      latest_version / activate / versions(skill_id)
class ContentPackageRepository: create / next_seq(skill_id) / by_status / assign_reviewer(...)
```

### 2.5 跨上下文共享聚合【关键设计】

**发现即产品**：Discovery 上下文采集的商品，在 Production 中被选定为「可交付产品」时直接复用同一 `Product` 聚合行（加 `product_role` 字段：`candidate → self-made`），避免重复建表。**评审事件联动**：

```
事件 ProductVerified        → Content.ProductAnalyst 触发「产品分析」Run
事件 SkillActivated         → 若 reviewPolicy=manual，通知人工；否则进入日更调度
事件 ContentGenerated       → 自动创建子审查 Run（审计要求独立于生成）
事件 ContentReviewed(pass)  → 状态 approved，可投递给发布通道（M5 预留）
```

消息总线初版用 PostgreSQL `LISTEN/NOTIFY` + 进程内事件（单机），预留换 Redis Pub/Sub / 消息队列接口。

### 4.2 分层规则（强制）

```
API(Router)  →  Service  →  领域服务 / 仓储
                      ↘  适配器（llm / playwright / adb / transcriber）
                      ↘  Agent 编排（tools → OpenAI 循环）
```

- Router 不做业务逻辑，只做参数校验与响应组装。
- Repository 持有 Session（Unit of Work），业务事务在 Service 层 `with uow`。
- 适配器对上层只暴露接口，不泄漏 Playwright/ADB 具体类型（可测试、可替换）。
- Agent 工具 handler 只能调用领域服务/仓储，禁止直接操作页面对象（保证可离线重放）。

### 4.3 统一响应与错误

```python
# 成功：{ "data": ..., "meta": { "total", "page", "page_size" } }
# 失败：{ "error": { "code": "PRODUCT_VALIDATION_FAILED", "message": "...", "details": [...] } }
```

| code | HTTP | 场景 |
|------|------|------|
| `AUTH_REQUIRED` / `PERMISSION_DENIED` | 401/403 | 未登录 / 越权 |
| `VALIDATION_ERROR` | 422 | Pydantic 校验失败 |
| `RESOURCE_NOT_FOUND` | 404 | 记录不存在 |
| `DEVICE_BUSY` | 409 | 手机/浏览器锁被占用 |
| `AGENT_RUN_IN_PROGRESS` | 409 | 同 Scope 已有在途 Run |
| `DEDUP_SKIPPED` | 200 | 去重跳过（写 meta 提示） |
| `PRODUCT_VALIDATION_FAILED` | 422 | 商品采集校验不齐 |
| `OPENAI_CALL_FAILED` | 502 | LLM 调用失败（附冲次建议） |
| `SKILL_NOT_ACTIVE` | 422 | 未激活 Skill 不可日更 |

## 五、接口契约（详细设计）

### 5.1 统一约定

- 鉴权：`Authorization: Bearer <jwt>`；刷新用 `POST /auth/refresh`。

## 六、Agent 编排引擎详细设计

### 6.1 运行时循环（伪代码）

```python
async def run_agent(def_: AgentDef, init_context: dict):
    uow = unit_of_work()
    run = AgentRun.create(def_, init_context)
    try:
        while True:
            resp = await llm.chat(
                model=def_.model,
                messages=run.messages + [{"role": "system", "content": def_.system_prompt}],
                tools=registry.tools_for(def_.tool_keys), temperature=def_.temperature,
            )
            msg = resp.choices[0].message
            run.messages.append(msg.model_dump())
            if not msg.tool_calls:
                run.finish(result=extract_json(msg.content)); break
            for call in msg.tool_calls:
                ok, out = registry.invoke(call.function.name, args=json.loads(call.function.arguments))
                run.tool_calls.append({"name":call.function.name, "args":..., "ok":ok, "out":out})
                run.messages.append({"role":"tool","tool_call_id":call.id,"content":json.dumps(out)})
            run.save()                       # 每个循环持久化（断点）
    except NeedsReview as e:                 # 工具抛出 → 置 BLOCKED
        run.status = "blocked"; ReviewPoint.create(run.id, e.rtype, e.payload); run.save()
    except RecoverableError as e:
        await RiskDelay.wait("common"); run.save()          # 指数退避内化
```

### 6.2 状态机

```
pending ──► running ──► done
              │  ▲
           blocked │  resume
              │  └─────► running（继续原上下文）
              │
              ▼
            failed（可 abort 重启，从 checkpoint 续）
```

- 超时：Agent 定义 `timeout`（默认 6h，千帆 单入口 20 页 × 90s ≈ 30~40min）。超时触发 abort + 告警，保留 killed 状态。
- 幂等复活：`continue_at` 到点由 Beat 扫描将 `pending`/`blocked(超时)` 重新入队。

### 6.4 Agent 提示词模板（关键 4 份）

**qianfan_collector（系统提示词）**
```
你是千帆数据中心榜单采集员。任务：逐一打开配置的榜单入口，按页采集榜单行。
规则：
1. 每次工具调用只处理一个 (source, page)，采集完立刻调用 qianfan_collect_ranking 返回该页结构化行。
2. 相邻两次调用之间由系统自动执行 60~90 秒随机延迟，你不要主动等待或臆想结果。
3. 一页返回后，判断：若已达 page_max 或返回空行，视为本入口结束，输出 { "finished": true, "entry": "<source>", "pages": N }。
4. 不得自行补充/编造榜单数据，所有字段必须来自工具返回值。
5. 不要在一个工具调用里塞多页，保持一页一次。
```

**account_analyzer（系统提示词）**
```
你是小红书虚拟产品账号分析师。输入：账号已入店的商品明细。
规则：
1. 一次只分析一个账号。
2. 必须输出的结论字段：主营品类、商品数量、价格区间(元)、最高销量商品(标题+销量)、
   产品形态(资料/模板/测评/教程/其他)、交付复杂度(低/中/高)、是否存在低粉高销(粉丝<1000 且出现千+销量)。
3. 事实必须来自给定商品数据，无法判断的字段写 unknown，不得臆测。
4. 完成后输出 JSON 结论；主 Agent 会用 direction_cluster 汇总。
```

**content_generator（系统提示词）**
```
你是小红书图文内容生产者。输入：产品总览文件路径 + 一份 Skill（含文件白名单与文案/图片规范）。
规则：
1. 只允许引用 Skill 文件白名单内的产品事实；严禁发明价格/功能/案例，违者将被审查驳回。
2. 严格套用 Skill 的标题公式与正文分段逻辑，不自行创造新结构。
3. 封面/内页文案按 Skill 图片规范产出；来源只能使用白名单截图或规范化排版。
4. 一次只产出 1 个内容包（标题/正文/话题/封面/内页）。
5. 输出用 content_generate 提交，提交即交付审查，不要自评。
```

**content_reviewer（系统提示词）**
```
你是独立内容审查员，与生成者分离。输入：同一产品资料 + 同一份 Skill + 待审内容包。
审查清单：
1. 事实准确性：任一价格/功能/效果/案例必须可溯源到白名单文件，否则驳回。
2. Skill 符合度：标题公式、正文结构、话题策略、禁用说法。
3. 图片质量：封面文字清晰度、内页分工与标注位置是否符合规范。
4. 互动可读性：开头钩子是否成立。
按清单逐条输出：{ passed: boolean, issues: [{type, message, ref}] }；
有一项不通过即 passed=false，附具体修改意见；不得为通过而通过。
```

### 6.5 生成↔审查轮转（核心保证）

```
content_generator Run 完成 → 事件 ContentGenerated
  → 服务创建 content_packages(reviewing, rounds+1)
  → 判定 skill.review_policy：
       manual → ReviewPost(REVIEW) 挂人工队列，WS 推送
       auto   → 立即创建 content_reviewer Run（独立 Celery 任务）

  → verdict=passed 或人工通过 → 状态 approved，可投递
```

### 7.2 ADB 手机驱动

- `adb driver` 封装原语（基于 `adbutils`）：

```python
class AdbDriver:
    def tap(self, text: str | None=None, bounds=None) -> bool      # UIAutomator 匹配节点并点击
    def find_and_click(self, desc: str, timeout=15) -> bool

- 店铺遍历剧本（`store_walker` 状态脚本，非 LLM 决策）：

```

  PROFILE_OPEN   → 找「店铺」点击 → STORE

- 同帧识别失败 N 次则触发 `adb_screenshot` 上报人工审查（UI 变化时定位器升级）。

## 八、调度、锁与延迟策略

### 8.1 Celery 拓扑

```
task 类型：
  oa.run.agent            # 通用执行体，参数 {run_uuid}
  beat:
    discovery.daily        # 每日 08:xx 启动 8 入口千帆采集（错峰）
    content.daily          # 每日 09:xx 未发布 Skill 日更 1 篇
    runs.release_stale     # 每 5 分钟复活 continue_at 到点的 Run
队列：
  default（API 同步性任务）
  agents（Agent Run，优先级中）
  scanning（采集类，跑锁校验后串行）
  review（审查类，快速）
```
- 单机 `--concurrency=1`；多机扩展时以 Redis 锁保证 device 单占。
- `acks_late=True, reject_on_worker_lost=True`；Run 状态落库，Worker 重启自动续跑。

### 8.2 设备锁（Redis）

```python
def acquire(device: str, run_id: int, ttl_sec=3600) -> bool:
    return redis.set(f"lock:{device}", run_id, nx=True, ex=ttl_sec)
# phone 与 browser 各自独立锁；agent_runs.checkpoint 每循环写心跳刷新 ttl，
# 心跳超 10 分钟视为僵死 → 报 blocked 并释放。
```

- 锁竞争失败 → Run 状态 `blocked(reason=DEVICE_BUSY)`，`continue_at=now+退避`，Beat 回扫续跑，前端置灰「运行中」按钮并提示占用 Run。

### 8.3 延迟与节奏

| 动作 | scope | 默认延迟 |
|------|-------|---------|
| 翻页 / 打开详情 / 下拉 | ranking / store / note | 60~90s（±10% jitter） |
| ADB 每动作 | store | 60~90s |
| 连续任务间隙 | common | 30~45s |
| 批量新增前 | common | ≥10s |

- 实现：`RiskDelay.wait(scope)` 读取 `risk_config`，`random.uniform(min,max)` 后 sleep；低延迟模式（测试环境 `risk_config.enabled=false`）直接跳过。

### 9.3 状态与数据流

```ts
// stores/taskCenter.ts (zustand)
{ activeRuns, blockedPoints, deviceLocks,
  apply_event(evt: WsEvent) }          // run.progress→更新行；run.blocked→写入审核队列

// hooks/useTasks.ts
subscribe_ws()  → 连接 /ws/tasks，onmessage 分发 store.apply_event
                断线重连（退避）+ 补拉 /tasks?after=lastSeenId

// react-query keys：['dashboard','summary']、['directions','list']…
// 页面只消费 query + store，写操作用 useMutation → 触发任务后由 WS 驱动刷新
```

- Dashboard 自动刷新：聚合统计；方向卡片用 `queryClient.invalidateQueries`（收到 `run.done` 时）。
- 任务中心实时日志：`run.progress.log_lines` 增量 append，限制展示最近 500 行，支持过滤 agent/级别。

### 9.4 关键组件

- `RunTimeline`：步骤+耗时+进度条（page/20）
- `ReviewPointModal`：审核点渲染（message + items + passed/rejected 表单），提交 `PATCH /review-points/{id}`
- `SkillEditor`：左侧 Markdown 编辑（monaco 可选 降级 textarea）+ 右侧预览 + 文件白名单 chips + 「试跑」&「上线」按钮（testing 通过才可上线）
- `DirectionCard`：状态 color 映射（观察中=默认、升温=processing、已验证=success、降温=warning、放弃=default）

## 十、异常体系、日志与可观测性

### 10.1 异常层级

```
AppError(业务错误, 携带 code/details)
 ├── AuthError / PermissionError
 ├── NotFoundError
 ├── DeviceBusyError / ConcurrencyError
 ├── ProductValidationError
 ├── ReviewRequired(触发 ReviewPoint)
 ├── TranscriptionError
 └── LlmError(可分类：timeout / rate_limit / bad_request)
RecoverableError(采集/网络可重试) → Run 内退避重试
FatalError(不可重试) → Run failed + 告警
```

### 10.2 日志

- **统一入库日志**：`agent_runs.log[]`（关键 tool 调用、错误、耗时），前端任务中心直接可看，无需查文件。
- **structlog** 结构化日志（`run_uuid`、`agent`、`device`、`source` 注入），滚动文件按天归档 `data/logs/`。
- **指标**（DB 表聚合即可，初版不做 Prometheus）：每日 accounts/products/notes 增量、Run 成功率、审查驳回率、平均单册时长。

### 10.3 审计关注点

- 人工判断（审核通过/驳回、定价、结构确认）一律记录 `action_by` 与 `action_note`。
- AI 结论与人工修正分列存 `reviews` / `skills` / 相关 JSONB，不互相覆盖。

## 十二、安全设计

1. **鉴权**：JWT access 2h + refresh 14d（服务端存 refresh 白名单可选）；角色仅 `operator/admin`，`settings` 路由仅 admin。
2. **密钥**：全部经环境变量注入，不落库、不进前端 bundle；`.env` 不入 git。
3. **上传安全**：资料/图片上传白名单扩展名 + 大小上限 + 走 `data/` 物理隔离（不做可执行）。
4. **敏感数据**：商品/账号数据仅本系统内部使用，导出走 `/export` 需 admin；日志脱敏（JWT、Cookie、share_link 尾号截断）。
5. **浏览器上下文隔离**：千帆与采集上下文分离，防越权/防脏数据交叉。
6. **风控**：默认延迟策略写死于 `risk_config`，任何人不可低于下限（admin 可临时禁用仅限 test profile 标记）。
